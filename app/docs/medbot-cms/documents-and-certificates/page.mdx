# Documents & Certificates

A patient's detail page lists their letters, memos, referral letters, and medical certificates — stored as FHIR `DocumentReference` resources in Medplum, including voided ones, which stay visible and labeled for audit.

## Who can compose what

Admins and doctors can compose all three free-text document types (letters, memos, referrals); nurses can compose letters and memos. Admins and doctors can issue medical certificates when their account has a linked Medplum practitioner and medical license number. Every clinic role can open an existing document and download, print, or email it as a PDF attachment.

Referral letters record a specialty (e.g. "ENT", "Cardiology") as a structured field alongside the free-text referral body, so the document list and PDF show who the referral is for at a glance.

## Medical certificates

Medical certificates support exactly three leave types: outpatient medical leave (not fit for work or school), light duty, and hospitalization leave. They record a start date, end date, inclusive day count, optional doctor comments, author license, and a location-specific annual serial such as `MAIN-MC-2026-000123`. The server computes the day count from the dates — it isn't entered by hand.

## Voiding

Any composed or issued document can be voided by the same roles that could have authored that kind (a nurse can void a memo but not a referral or certificate). Voiding never deletes the resource, edits it in place, or reclaims an MC serial — it marks the `DocumentReference` `entered-in-error` and records who voided it, when, and why. Correcting a mistake means voiding the original and composing/issuing a new one. A voided document can still be viewed, but can no longer be downloaded, printed, or emailed.

## Storage

Document type, recipient details, structured certificate fields, referral specialty, void metadata, and the public verification token all live as local FHIR codes and extensions on the `DocumentReference` — Postgres stores only non-clinical operational state: the atomic serial counter in `document_serials`, and a hashed reverse-index from verification token to document in `document_verification_tokens`. To enable email delivery, configure a Resend API key and a sender address on a verified domain:

```bash
RESEND_API_KEY=your_resend_api_key
RESEND_FROM_EMAIL=Medbot Clinic <documents@yourclinic.example>
```

## Document verification

Every composed or issued document gets a QR code (and a printed link) on its PDF, linking to an unauthenticated `/verify/{token}` page. Anyone who scans it — an employer confirming a medical certificate, a school confirming a memo — sees only whether the document is currently valid or has been voided, plus non-clinical identifying details (patient name, document type, issuer, date, and MC leave type/dates/serial). It never shows the letter or memo body, or MC comments, since those can carry a diagnosis or other detail that isn't the verifier's business.

Voiding a document does not invalidate its QR code — the verification page still resolves, now showing "voided", which is the point: a forged or superseded certificate should visibly fail verification rather than 404.

Set `NEXT_PUBLIC_APP_URL` to the deployment's real base URL in production so QR codes point at it instead of localhost:

```bash
NEXT_PUBLIC_APP_URL=https://cms.yourclinic.example
```
