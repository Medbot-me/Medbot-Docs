# Gateway (Developers)

This page is for engineers working on the Medbot API. It describes how `apps/api` talks to SmartCMS: configuration, authentication, envelopes, outcomes, the submission outbox, sequencing, the evidence log, entitlements, scheduled jobs, the MCP claims server, and the mock gateway used in development and tests.

> **Status.** The CHAS, Screen for Life, VCDSS, Medisave, NIR, CIDC, DEROM, MW Health and NEHR workflows all call SmartCMS through this gateway: enquiries directly, submissions by way of the submission outbox. Everything is built and tested against the mock gateway only. **Nothing has been sent to Synapxe UAT yet**, and some envelope and route details are still open questions with Synapxe (see [the end of this page](#open-questions-with-synapxe)).

## Configuration

SmartCMS is **off** unless `SMARTCMS_ENABLED=true`. When it is on, every variable below is validated at start-up and the API refuses to boot, naming each bad key, if any is wrong. The configuration is per deployment, not per clinic.

| Variable | Required | Notes |
| --- | --- | --- |
| `SMARTCMS_ENABLED` | | `true` to turn the gateway on. Anything else leaves it off. |
| `SMARTCMS_ENV` | Yes | `uat` or `prod`. Calls are only made for locations entitled in this environment. |
| `SMARTCMS_BASE_URL` | Yes | The CAG base URL. Must be `https`, except to a loopback host. |
| `SMARTCMS_API_KEY` | Yes | Sent as `x-api-key`. |
| `SMARTCMS_JWT_KID` | Yes | JWT header `kid`. |
| `SMARTCMS_JWT_ISS` | Yes | JWT `iss`. |
| `SMARTCMS_JWT_SUB` | Yes | JWT `sub`. |
| `SMARTCMS_JWT_PRIVATE_KEY_PEM` | Yes | PKCS#8 RSA key, at least 2048 bits. `\n` escapes are accepted. |
| `SMARTCMS_SRC_APPLICATION` | Yes | `controlHeader.srcApplication`, up to 50 characters. |
| `SMARTCMS_DOMAIN_SOURCE_ID` | Yes | Becomes `NC_<id>` in the legacy envelope. |
| `SMARTCMS_JWT_TTL_SECONDS` | No | 30 to 180, default 120. |
| `SMARTCMS_HTTP_TIMEOUT_MS` | No | Default 20000. At least 1000 and **below 120000**, the outbox's dispatch lease. |
| `SMARTCMS_ENVELOPE_OVERRIDES` | No | JSON map of route to `scg-json`, `scg-xml` or `legacy-isb-xml`, overriding the registry default. |
| `SMARTCMS_BARE_XML_ROUTES` | No | JSON array of `scg-xml` routes whose envelope goes out without the SOAP wrapper, as the NIR samples are. |
| `SMARTCMS_CDMP_SENDER_MAILBOX` | No | The UCFMSG sender mailbox SCG issues for CDMP. Without it Medisave claims wait in `prepared`. |
| `SMARTCMS_DEROM_SERVICE_INTERFACE_ID` | No | DROM's `ServiceInterfaceID`, once Synapxe issues one. |
| `SMARTCMS_OAUTH_REDIRECT_ORIGINS` | No | Origins an MCP connector may redirect to. Default `https://claude.ai` and `https://claude.com`, plus loopback. |

Start-up also fails when:

- an override or bare-XML route is not a SmartCMS route, or its variant cannot carry the service's format (a JSON service only takes `scg-json`; `legacy-isb-xml` only where the service has a legacy form; only `scg-xml` can go bare);
- `SMARTCMS_BASE_URL` is a documented gateway host for the other environment: `cag-uat.synapxe.sg` is UAT and `api.healthiersg.com.sg` is production, so UAT credentials never reach production and the reverse;
- `SMARTCMS_HTTP_TIMEOUT_MS` is at or above the 120 s lease. A call still in flight would lose its lease, and the sweep could hand the same submission to a second dispatcher.

The evidence log also uses the organisation secrets key: `ORGANISATION_SECRETS_KEY`, `ORGANISATION_SECRETS_KEY_VERSION` and `ORGANISATION_SECRETS_KEY_PREVIOUS`.

## Authentication

Every request to CAG carries:

- `x-api-key`: the API key.
- `Authorization: Bearer <jwt>`: an **RS256** JWT with `kid`, `iss`, `sub`, `iat`, `exp` and a fresh UUID `jti` for every attempt. The signer (`transport/jwt-signer.ts`) is behind a `JwtSigner` interface so a KMS-backed signer can replace the PEM one.
- `ServiceType`: equal to the envelope's `controlHeader.serviceType`.

## Envelopes

A SmartCMS message is an `SCG_RequestInfo` with a **control header** and a string `messageContent`; the reply is an `SCG_ResponseInfo` that adds a `status`.

| Control header field | Notes |
| --- | --- |
| `srcInstitution` | The location's **HE code**. |
| `srcApplication` | `SMARTCMS_SRC_APPLICATION`. |
| `msgID` | A new UUID per attempt. |
| `msgSequenceID` | From the sequence allocator, at most 15 digits. |
| `msgDateTime` | Singapore time, `YYYY-MM-DDThh:mm:ss.sss+08:00`. Received times may have any number of fractional digits. |
| `serviceType` | The registry's wire service type. |

Three codecs encode requests and decode replies (`transport/envelope/`):

| Variant | Shape |
| --- | --- |
| `scg-json` | The SCG envelope as JSON. Default for JSON services. |
| `scg-xml` | Default for XML services. Written as `<scg:Root xmlns:scg="…">` with **unqualified** children, as every SCG schema requires; a default namespace would put the children in the SCG namespace and fail validation. Screen for Life uses `SCG_SFL_RequestInfo` with an `eCHAS` element (and `EISS` for S/N 11). NIR uses `SCG_NIR_RequestInfo` in `http://www.mohh.com/scg/Request`. Sent in a SOAP 1.1 body unless the route is in `SMARTCMS_BARE_XML_ROUTES`. |
| `legacy-isb-xml` | The older AP481 envelope, built from each service's WSDL (wrapper, namespaces, `SOAPAction`). Only S/N 1 to 3 and 12 to 16 have one. |

Envelopes are checked per S/N against the vendor XSDs in tests, with libxml2 (`xmllint-wasm`).

Decoding is lenient: any `SCG_*ResponseInfo` root in any namespace, with or without the SOAP wrapper, children by local name. The status is read even when the control header is invalid, because the status alone classifies the call.

**MSB.** CHAS, eCHAS and EISS answers may arrive inside an MSB `Response` with the payload under `ContextBody` → `Content`. Every reader takes both the bare payload and the MSB-wrapped one (`xml/msb.ts`), because whether SCG strips the wrapper is still open. MSB statuses are mapped too: a write answered with a failure MSB does not document as "not acted on" may have been applied, so it is treated as unknown.

Which envelope CAG expects per route is still an open question with Synapxe, which is why `SMARTCMS_ENVELOPE_OVERRIDES` and `SMARTCMS_BARE_XML_ROUTES` exist.

### Identifiers

- NRIC and FIN check letters have one implementation, `identifiers.ts` in the contract, used by every Medbot surface. M-series FINs (issued from 2022) use the GovTech FormSG table.
- An MCR number is `M`, five digits and a letter (`MCR_PATTERN` in `@repo/authz`).
- NEHR identifies a patient without an NRIC by passport.
- Hex message ids are not mistaken for NRICs.

### SCG status codes

| Code | Meaning |
| --- | --- |
| `SCG_00` | OK |
| `SCG_01` | Technical error |
| `SCG_02` | Invalid service type |
| `SCG_03` | Duplicate message |
| `SCG_04` | Invalid application |
| `SCG_05` | Invalid institution |
| `SCG_06` | Not allowed |
| `SCG_07` | `messageContent` issue |
| `SCG_08` | No email configured for PHI |
| `SCG_09` | Invalid format (HTTP 400) |
| `SCG_99` | Missing headers (HTTP 400) |

Legacy (AP481) statuses are classified by each service family's own error table (`transport/legacy-status.ts`).

## Making a call

The rest of the API calls SmartCMS only through `SmartcmsGatewayService.call(...)`, passing the organisation, the clinic location, the service and the message content (plus optional submission id, attempt, acting member and patient reference). In order, it:

1. Checks the kill switch (`SMARTCMS_ENABLED`).
2. Checks the location's subscription, its **entitlement** for the configured environment, and its HE code. A refusal throws `SmartcmsNotEntitledError` and nothing is sent.
3. Allocates one **sequence number**.
4. Writes the **request** to the evidence log. If that write fails, nothing is sent.
5. Sends one attempt through `SmartcmsGatewayClient`.
6. Writes the **response** (or timeout, or transport error) to the evidence log. A failure here is logged, and the result is still returned.

Services whose group has no module (CHAS_DENTAL, ALPS, PSS, LEGACY) cannot pass step 2. The planned modules (CMIS, HSG_BUNDLE) can be subscribed to, but no code calls their services yet. S/N 25 has no route, so the client refuses it.

### Outcomes, not exceptions

The client throws only for local problems: SmartCMS is disabled, or the service has no route. Anything that happens remotely comes back as a `GatewayOutcome`, with the raw request and response bodies:

| Outcome | Meaning |
| --- | --- |
| `accepted` | SCG accepted the message. |
| `rejected_before_backend` | Rejected by CAG/SCG before reaching the back-end. `fix` says whether the cause is `config`, `code` or `data`. |
| `rejected_unknown_reach` | Rejected, and it is unknown whether the back-end saw it. |
| `not_authorised` | Authentication or entitlement refused. |
| `rejected_legacy` | A legacy-envelope rejection, with what the service's AP481 error table says it means. |
| `timeout` | No reply within the timeout, from CAG or the client. |
| `transport_error` | Connection-level failure, noting whether any of the request was sent. |

`outcomePolicy()` (`transport/classify.ts`) maps each outcome to whether an enquiry may retry once, the resulting submission state, and whether to alert (`no`, `yes` or `if_repeated`).

## The submission outbox

Every submission goes through `smartcms_submissions`. `SmartcmsSubmissionService` is the only write path, shared by staff screens, domain-event handlers, MCP tools and jobs.

- **One live row per business key**, for example `chas:{encounterId}:ACT`, `nir:{immunizationId}` or `derom:{encounterId}:{disease}`. A replayed event or a second prepare finds the existing row. This is Medbot's layer of double-claim prevention.
- **States:** `prepared`, `pending`, `dispatching`, `acknowledged`, `completed`, `failed_retryable`, `failed_terminal`, `outcome_unknown`, `cancelled` and `superseded`.
- **Resubmission.** A claim MHCP rejected is never sent again from its own row. `POST /smartcms/claims/:id/resubmit` (admin only, `SMARTCMS_RESUBMIT_ROLES`; never an agent or job) prepares the claim again from the visit's current bill as a new row under `{key}@{n}`, and moves the rejected row from `completed` to `superseded`, keeping its adjudication. Agents and jobs keep finding the rejected row under the unsuffixed key, so they never prepare the visit's claim again. A resubmission and an appeal of one rejection exclude each other, and both take a per-claim decision lock. A voided bill's claims are released attempt by attempt (`{key}@2`, `@3`, …); a `superseded` row is left alone.
- **Who may promote.** A person's Submit, or an agent under `auto_submit` for CHAS, CDMP, NIR and MW Health, moves `prepared` to `pending`. **DEROM and CIDC rows are only ever promoted from their report form, by a doctor.** A row whose draft lists issues is refused with `draft_incomplete`.
- **Entitlement is not checked on write.** A row may exist while its location is `off`; dispatch checks again.

Becoming `pending` emits `smartcms/submission.pending`, which starts the `smartcms-dispatch` function.

### Dispatch and retries

One dispatch is one attempt. It takes a **lease** on the row (2 minutes), runs the service's mapper on current data, renews the lease, calls the gateway, and records the next state. Every write that ends an attempt is conditioned on the attempt number, so a dispatcher that lost its lease cannot record over another.

| What happened | Next state |
| --- | --- |
| Accepted | `acknowledged`, or the mapper's verdict (`completed`, `failed_terminal`, `failed_retryable` when the back-end asks to try later, `outcome_unknown` for an unreadable answer) |
| Nothing was sent (connection refused) | `failed_retryable`, retried after **1, 5 and 15 minutes**, then `failed_terminal` |
| May have reached the back-end: a timeout, `SCG_01`, `SCG_03`, a reset, or any error once the request was logged | `outcome_unknown`, **never resent automatically** |
| Rejected before the back-end | `failed_terminal` |
| The mapper refuses the data | A claim goes back to `prepared`, held with the issue; anything else `failed_terminal` |
| The location is not (or no longer) entitled, in the wrong environment, has no HE code, or SmartCMS is off | Back to `pending` untouched. The row is **parked** until the entitlement is fixed. |

CHAS and MSB `DOWNTIME_EXCEPTION`, and NIR `ERR_SYSTEM` and `ERR_NOT_WITHIN_OPS_HR`, are retried on the same backoff.

The client itself never retries: each attempt needs a new `msgID`, and `SCG_03` is the gateway's duplicate detection on the control header. Medbot never reuses a control header. Only enquiries are safe to retry blindly.

### The stale-submission sweep

`smartcms-stale-submission-sweep` runs hourly at :15. It:

- reclaims expired leases: `outcome_unknown` if the attempt's request may have left (its evidence row exists), else `pending` again;
- offers `pending` rows idle for ten minutes, and `failed_retryable` rows overdue by ten, to dispatch again (this is how parked rows are retried);
- cancels claims (CHAS, CDMP, SFL) an **agent** prepared and nobody touched for seven days. A person's or a job's rows are never cancelled, and no report or registry row is;
- alerts once on a report waiting `prepared` past its deadline (DEROM a day; CIDC, MW Health, held NIR rows and held NEHR letters a week), on `outcome_unknown` rows a working day old, and on rows parked by entitlement for a working day;
- then, as its own step (`cdmp-advice-monitor`), runs the **30-day CPF advice monitor** (`SmartcmsCdmpAdviceMonitor`). SCG keeps a CPFADV for 30 days, so a Medisave claim (S/N 12) still `acknowledged` with no advice or error matched to it is marked `lastErrorCode` `CPF_ADVICE_OVERDUE` 20 days after it was sent and `CPF_ADVICE_ESCALATED` at 25, each once, with alert kinds `cpf_advice_overdue` and `cpf_advice_escalated`. The claims queue lists both under needs-attention. CPF's answer replaces the code, or clears it for `AI` and `PN`.

### Domain events

The CMS announces writes it makes straight to Medplum through `POST /domain-events` (for example `medbot/invoice.issued`, `medbot/immunization.recorded`, `medbot/referral.issued`); `apps/api` emits `visit.completed` itself. Each event has a `smartcms-on-*` Inngest function. Every handler first passes a shared gate: the organisation is in Singapore, subscribes to the handler's group, and, when the event names a location, that location is entitled in the configured environment. Handlers re-read the source record, so a forged event does nothing.

## Sequencing

`smartcms_sequences` keeps one counter per **HE code**, **wire service type** and **environment**. Each allocation is a single upsert starting at 1. Gaps are allowed; repeats are not. Allocation fails past 15 digits.

## Evidence log

`smartcms_messages` records **one row per attempt**, written before sending and completed afterwards. It is unique on submission and attempt.

- Request and response **bodies are encrypted** with the organisation secrets key and bound to the organisation.
- `x-api-key` and `Authorization` headers are **never stored**.
- Plaintext columns support lookup and audit: service type, route, environment, envelope variant, `msg_id`, sequence, `msg_date_time`, JWT `jti` and key id, attempt, HTTP status, SCG status, business status code, outcome (`success`, `business_rejection`, `gateway_error`, `transport_error`, `timeout`), latency, the acting member, and `patient_ref` as a `Patient/<id>` reference, **never an NRIC**.

**SIT evidence export.** An admin can export one message (`GET /smartcms/evidence/:msgId`) or every message of a SIT tag as one text file per `msgID`, with the full request (headers without secrets) and response. SIT runs open a window at one location and only on a deployment configured for `uat`. Every export decrypts PHI, so it is written to `audit_events` first; a failed audit write fails the export. See [SmartCMS Settings](/cms/smartcms/settings#sit-evidence).

How long the log must be kept is still open.

## Entitlements

`smartcms_entitlements` holds one row per **clinic location** and **service group**, with an `environment` (`off`, `uat`, `prod`), a Synapxe reference, an optional agent-policy override, a MOM organisation code (for migrant worker health), and who last changed it.

- **Sync.** When an organisation is updated, the API publishes `medbot/organisation.updated`. The Inngest function `smartcms-entitlements-sync` creates `off` rows for every location and every group of every subscribed module (Screen for Life creates both SFL and CHAS rows), and turns rows for dropped modules `off`. Rows are never deleted.
- **Setting one.** An admin sets a location's entitlement to `uat` or `prod` on the [SmartCMS settings](/cms/smartcms/settings) page (`/organisations/[id]/smartcms`), through `PUT /organisations/:orgId/smartcms/locations/:locationId/entitlements/:group`. The same page runs the connection test (S/N 7, the accreditation status query, for the location's own HE code) and the onboarding export. Changing a location's HE code or Hospital Code switches its approvals off.
- **Check.** `requireEntitled` refuses, in order, with `unknown_location`, `not_singapore`, `not_subscribed`, `not_entitled`, `wrong_environment` or `no_he_code`.
- **Route guard.** `@RequireSmartcmsModule(...)` with `SmartcmsModuleGuard` fails closed with 403 outside Singapore or without the module. When the route names a location, via a `:locationId` parameter or the `X-Clinic-Location-Id` header, it checks that location's entitlement too. Every staff-facing SmartCMS controller uses it, alongside the staff role guard. The MCP and OAuth routes have their own guards.

## Scheduled jobs

All times are Singapore time (SGT).

| Function | Schedule | What it does |

| `smartcms-cdmp-status-pull` | 09:00, 13:00 and 18:00, Monday to Friday | Pulls CPF's advice (CPFADV) on Medisave claims from every CDMP mailbox. A message that matches no claim is kept `unmatched` for staff (see [below](#cdmp-mailbox)). |

| `smartcms-invoice-claims-sweep` | 02:30 daily | Replays `medbot/invoice.issued` for a week's issued bills whose claim never reached the outbox, and alerts on a bill already replayed that still has none. |

## CDMP mailbox

CPF answers Medisave claims through the CDMP mailbox (S/N 13). `SmartcmsCdmpStatusService` stores each message once, raw, then matches it: a CPFADV by HRN, submission type and the submission date and time CPF echoes; an ERRMSG by the `UNH` reference of the UCFMSG it refuses. A message that matches no claim is kept `unmatched`; one that cannot be read, `error`.

Staff settle `unmatched` messages from the Medisave payments page, through `smartcms/cdmp/mailbox` (`SMARTCMS_MEDISAVE_ROLES`, module guard):

| Route | What it does |
| --- | --- |
| `POST /smartcms/cdmp/mailbox/pull` | "Check CPF now": pulls one location's mailbox outside the schedule. |
| `GET /smartcms/cdmp/mailbox/unmatched` | The unmatched messages, newest first, each with up to 25 candidate claims (`MedisaveUnmatchedMessage`). An advice's candidates are the location's sent claims under its HRN and of its submission type; an error notice's, the location's latest. Optional `clinicLocationId`. |
| `POST /smartcms/cdmp/mailbox/unmatched/:messageId/match` | `{submissionId}`: applies the message to that claim exactly as a pulled one (`ClaimResponse` first, then the claim status row and outbox state). Refused unless the claim is a sent Medisave claim of the message's location and, for an advice, under its HRN and submission type. If applying fails, the message goes back to `unmatched` (503). |
| `POST /smartcms/cdmp/mailbox/unmatched/:messageId/dismiss` | Marks the message `dismissed` as not Medbot's. It is kept. |

Match and dismiss are scoped to the organisation and audited (`cdmp_message.match`, `cdmp_message.dismiss`). A second settle of the same message answers 409.

**Tie-outs.** `tieOuts()` (`cdmp-recon.service.ts`) ties out every submission type CPFSUM or CPFPAY names, in the order `FS`, `AM`, `CA`, then any other. `AM` and `CA` refunds are negative. A type in only one file is tied out against zero, so it shows as a difference rather than not at all.

## Claims day view

`GET /smartcms/claims/day?locationId=&date=` (`SMARTCMS_CLAIMS_VIEW_ROLES`) returns `ClaimsDay`: every visit checked in at the location on that Singapore date, with its live bill, the bill's claims as the queue shows them (resubmissions included), what the patient owes (`owed`) and their payments. `paymentsVisible` is true only for `QUEUE_RECEPTION_ROLES`; for anyone else the rows carry no payments. What a visit owes is computed once, by `visitOwedOf` in `@repo/smartcms-contract` (`claims-owed.ts`), which the counter's Take payment and the CMS day view share. A claim's amount is the bill's figure for its business key, never the cleared draft.

## MCP claims server

`/mcp/smartcms` is a stateless MCP server that offers the SmartCMS claims tools to AI agents: listing claimable visits, CHAS and Medisave enquiries, preparing claims and reports, submitting under `auto_submit`, reading the queue and reconciliation, and flagging work for staff. Its only writes go through `SmartcmsSubmissionService`, and the organisation and location always come from the caller's credential, never from a tool argument.

- **Who may call it.** An agent credential, checked by `SmartcmsAgentGuard`, or a staff session with the admin or receptionist role in a Singapore organisation with a SmartCMS module. Every refused token answers 401 with a `WWW-Authenticate` bearer challenge.
- **OAuth.** A connector discovers the CMS as authorisation server through `/.well-known/oauth-protected-resource/mcp/smartcms`, registers a public client, and sends an admin to a consent page. The approved code (PKCE `S256`) is exchanged for an ordinary location-bound agent credential lasting 7, 14 or 30 days. There are no refresh tokens. A replayed code revokes the credential it produced. Public OAuth routes are throttled, and each caller's CHAS and Medisave enquiries are rate-limited.
- **Agent rules.** DEROM and CIDC always wait for a doctor, and appeals and resubmissions are never offered to an agent.

For the user side, see [Claims Agent](/cms/smartcms/claims-agent).

## The mock gateway

`apps/api/test/smartcms-mock/` is a plain `node:http` server that plays CAG, SCG and fake back-ends, for local development and tests.

### Running it

```bash
pnpm --filter medbot-api smartcms-mock
```

| Variable | Default |
| --- | --- |
| `SMARTCMS_MOCK_PORT` | `4455` |
| `SMARTCMS_MOCK_PUBLIC_KEY` | Path to a PEM public key. Without it, the mock generates a key pair and prints the private key's path. |
| `SMARTCMS_MOCK_KID` | `MEDBOT-01` |
| `SMARTCMS_MOCK_ISSUER` | `MEDBOT` |
| `SMARTCMS_MOCK_SUBJECT` | `MEDBOT` |

It prints the API key to use (`smartcms-mock-api-key`). The expected `srcApplication` is `MEDBOT`. Two HE codes are seeded: `9400001` (entitled to CHAS, SFL, CDMP, MW_HEALTH, NIR, CIDC, DEROM and NEHR_REFERRAL) and `9400002` (no service groups, so every call answers `SCG_06`).

To point a local API at it, set `SMARTCMS_ENABLED=true`, `SMARTCMS_ENV=uat`, `SMARTCMS_BASE_URL=http://localhost:4455`, the printed API key and private key, and matching `kid`/`iss`/`sub`.

In tests, start it in-process with `startSmartcmsMock({ consumers })`.

### What it checks

- **CAG:** the API key; the JWT's `kid`, `iss` and `sub`; `iat` within 60 seconds; `exp - iat` at most 180 seconds; a `jti` of at least 36 characters that has not been seen before. Failures answer 401 with a reason. CAG times out at 15 seconds (504) while the back-end keeps running, as the real one does.
- **SCG:** the envelope, validated against the vendor XSDs; each route takes only its own format, and the legacy form only where the route has one; every status code from `SCG_01` to `SCG_99`. A reused `msgSequenceID` for the same `srcInstitution` and `serviceType` answers `SCG_09`.
- **Back-ends:** S/N 1 to 4, 7 to 16, 19, 24, 38, 39 and 47. Any other service answers `SCG_01`.
